# 审核标准

维护者合并投稿前按以下顺序检查。自动检查（“检查”工作流）通过是前提；它管格式、文件位置、授权状态、许可与重复，下面几条需要人工判断。

## 0. 先看改了什么

- 投稿 Pull Request 只能改 `cheers/`；自动检查会拒绝把投稿和其他修改混在一起的 Pull Request。
- 自动检查用的是**基准分支**的检查代码，Pull Request 自带的 `lib/`、`tools/` 修改不会影响它的结果。反过来，修改 `lib/`、`tools/`、`tests/`、`spec/`、`.github/` 或 `package.json` 的 Pull Request，检查通过不代表修改正确，须逐行审查；工作流文件的修改尤其要看权限与触发条件。
- 本仓库设置为第一次投稿者的工作流须经维护者批准：在 Pull Request 页面先看一眼改动，再点 **Approve and run**。

## 1. 授权是否可信

- `original`：文件应是投稿者自己听写打轴的。看说明是否具体（例如怎样听写、参考了哪一场演出的录音）；如果与某份公开的 call 表或某个视频的时间轴几乎一样，请投稿者说明，必要时不收。
- `open-license`：打开来源链接，确认许可确实是 `license` 写的那一种，且允许修改与再分享；相同方式共享（SA）的来源只能以 `CC-BY-SA-4.0` 发布。
- `consented`：Pull Request 中须有原作者同意的链接或可核对的说明（例如原作者在公开页面上的回复）。只有截图、无法核对时，请投稿者补充。

## 2. 没有歌词原文

- 通读每条口号、call 与提示：应当是 MIX、成员名、短的喊声或动作提示，不是唱词。
- 跟唱的那一句应当用 `echo`，不写文字。
- 有疑问时，在映场中导入该文件并播放这首歌，再点“分享…”：映场会把文字与歌词逐行比对（`lyricOverlap`）。

## 3. 内容适当

- 不收侮辱、骚扰、歧视或涉及私人信息的内容；作者署名与链接只能是投稿者本人的。
- 不收与应援无关的文件。
- 某个组合专属的口号可以出现在那首歌的文件里；内置 MIX 库（`spec/mix-library.json`）只收通用 MIX，按 [投稿指南](../CONTRIBUTING.md) §7 的标准，至少两个独立公开来源交叉核对。

## 4. 重复与更新

- 内容完全相同的文件，自动检查会拒绝。
- 检查提示“同一作者已有这首歌的版本”时，问投稿者是否要替换旧文件。
- 不同作者为同一首歌做的版本可以并存。

## 5. 合并

- 用 “Squash and merge” 合并，保留投稿者为作者。
- 合并后“更新索引”工作流会自动提交新的 `index.json`。如果它失败（例如推送时 `main` 已有新提交），在 Actions 页面选“更新索引”，点 **Run workflow** 从最新的 `main` 重新运行；不要用“重新运行”旧的那一次，它会取出旧提交。

## 下架

收到下架请求时按[下架规则](./takedown.md)处理，不在这里等待审核流程。
