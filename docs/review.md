# 审核标准

维护者合并投稿前按以下顺序检查。自动检查（“检查”工作流）通过是前提；它管格式、文件位置、授权状态、许可与重复，下面几条需要人工判断。

## 0. 先看改了什么

- 投稿 Pull Request 只能改 `cheers/` 与 `mix/` 下的投稿文件（`mix/proposals/`、`mix/artists/`）；自动检查会拒绝把投稿和其他修改混在一起的 Pull Request。修改 `contributors.json` 的 Pull Request 会影响原投稿者身份的核对，须逐项核对。
- 自动检查用的是**基准分支**的检查代码，Pull Request 自带的 `lib/`、`tools/` 修改不会影响它的结果。反过来，修改 `lib/`、`tools/`、`tests/`、`spec/`、`.github/` 或 `package.json` 的 Pull Request，检查通过不代表修改正确，须逐行审查；工作流文件的修改尤其要看权限与触发条件。
- 本仓库设置为第一次投稿者的工作流须经维护者批准：在 Pull Request 页面先看一眼改动，再点 **Approve and run**。

## 1. 授权是否可信

- `original`：文件应是投稿者自己听写打轴的。看说明是否具体（例如怎样听写、参考了哪一场演出的录音）；如果与某份公开的 call 表或某个视频的时间轴几乎一样，请投稿者说明，必要时不收。
- `open-license`：打开来源链接，确认许可确实是 `license` 写的那一种，且允许修改与再分享；相同方式共享（SA）的来源只能以 `CC-BY-SA-4.0` 发布。
- `consented`：Pull Request 中须有原作者同意的链接或可核对的说明（例如原作者在公开页面上的回复）。只有截图、无法核对时，请投稿者补充。

## 2. 没有歌词原文

- 通读每条口号、call 与提示：应当是 MIX、成员名、短的喊声或动作提示，不是唱词。
- 跟唱的那一句应当用 `echo`，不写文字。
- 有疑问时，在映场中导入该文件并播放这首歌，再点“分享…”：映场会把文字与歌词逐行比对（`lyricOverlap`）。

## 3. 内容适当

- 不收侮辱、骚扰、歧视或涉及私人信息的内容；作者署名与链接只能是投稿者本人的。
- 不收与应援无关的文件。
- 某个组合专属的口号可以出现在那首歌的文件里，也可以作为艺人专属 MIX 投稿；内置 MIX 库（`spec/mix-library.json`）只收通用 MIX，见 §7。

## 4. 重复与更新

- 内容完全相同的文件，自动检查会拒绝。
- 检查提示“同一作者已有这首歌的版本”时，问投稿者是否要替换旧文件。
- 不同作者为同一首歌做的版本可以并存。

## 5. 合并

- 用 “Squash and merge” 合并；免账号投稿的署名看应援文件与 PR 说明，Git 提交账号是代投机器人。
- 合并后没有工作流写回 `main`。Cloudflare Pages 收到这次合并后重新构建网站，首页与网站的 `index.json` 由构建从 `cheers/`、`mix/` 现场生成；仓库里不存放 `index.json`。构建失败时网站停在上一版，在 Cloudflare 的部署页面看日志并重试，或等下一次合并。
- `contributors.json` 与通用 MIX 的并入不随每次合并更新。需要时在 Actions 页面选“更新记录”，点 **Run workflow**：它把结果提交到一个 `records/` 分支并给出发起 Pull Request 的链接，由维护者发起、按 §6 核准后合并。记录落后期间，相关文件的修改只认维护者的核准。

## 6. 各类投稿如何合并

| PR 的全部改动 | 处理方式 |
| --- | --- |
| 仅新增应援文件或艺人专属 MIX | 检查全部通过后自动 Squash 合并。同一 PR 可含多份新增文件。 |
| 修改、替换、改名或删除已有文件 | 逐份取得原作者或维护者对当前改动的批准，由维护者手工合并。作者本人发起也走人工流程。 |
| 通用 MIX 提议、内置库的任何改动，或混合其他改动 | 一律由维护者审核并手工合并。代码、配置、贡献者记录也走人工审核。 |

已有文件用 `contributors.json` 的 GitHub 账号数字编号核对。原作者或仓库维护者审核全文后，在该 PR **新发一条评论**，只写 `/cheerbook approve <40 位完整 PR 提交 SHA>`（在 PR 的 Commits 页复制最新提交号）。工作流用 GitHub 返回的评论者 ID 核验；改过的评论或旧提交的批准无效。多人投稿同时修改时需要每份已有文件对应的原作者都同意，或由维护者统一批准。维护者可在自己的 PR 上使用相同命令。免账号投稿的昵称、公开主页或代投机器人均不能证明来者就是原作者。没有可靠作者记录时，由维护者查来源和修订理由，在 PR 中写明批准后合并。公开主页可供联系，代投账号不记为原作者。作者没有 GitHub 账号时可像首次投稿一样提修订，无须编辑令牌。

自动合并只接受 GitHub 报告的完整新增清单，核对同一提交在当前主分支上的实际合并树，只收普通数据文件，再重跑社区检查。真实世界的版权与唱词出处仍可能需要人工核实，收到反馈按下架规则处理。自动合并排队逐个写入，GitHub 最多排队 100 项，超出后检查 Actions 并重跑。GitHub 合并接口只锁定投稿提交。若要让平台同时阻止基准在最后一刻前移，在 `main` 设 `check` 与 `cheerbook/review-policy` 为必需状态检查、来源选 GitHub Actions，并要求分支最新，绕过名单留空；合并后已没有任何工作流直接推送 `main`，所以不需要为 GitHub Actions 或投稿机器人放行。另一份投稿先合并后，仍打开的投稿会落后于 `main`，在该 PR 点 **Update branch** 即可重新检查并自动合并。保护启用前，这个条件性状态显示结果，仓库有合并权限的人仍可手动忽略它；单一维护者只在它通过后执行人工合并。开放免账号投稿前、以及额外协作者接入前须落实保护。

## 7. MIX 投稿

先确认“检查”通过（格式、读音个数、编号与路径、来源链接、与内置库不重复都由它检查），再看：

- **通用 MIX 提议**（`mix/proposals/`）：
  - 入库标准草案：提交多个不同艺人现场实际使用同一口号的可核查证据，列明艺人、公演、公开来源和时间点（或可定位段落）。来源数量与不同艺人的场数是两件事；具体艺人及场次数量门槛待维护者确认。本期无投票。
  - 是否通用：名称在应援圈公认，形式在各来源中基本一致；不含特定成员、组合、公演名或专属梗（成员名字只能是 `{name}` 空位）。属于某个组合的，请投稿者改投艺人专属 MIX。
  - 打开每个来源链接，确认能看到这条口号，且来源之间相互独立（不是互相转载）；只在单一来源出现、或来源之间差异大的不收。
  - 核对平假名与罗马音（逐词与整句），特殊读法要有 `readingNote`；`note` 是投稿者自己的话，不是照搬来源的说明。
  - 合并提议后，手动运行“更新记录”：它运行 `tools/accept-mix-proposals.js`，把提议追加到内置库末尾（沿用已有来源代码或分配新代码）并删除提议文件，提交到 `records/` 分支；由维护者发起 Pull Request、核准后合并，之后才算入库。它失败时整次运行失败、不会只并入一半，修正后重新运行。“检查”只在提议文件被删除时放行“提议文件与 `spec/mix-library.json` 同时改动”；新增提议的 PR 仍不能同时改内置库。内置库变了之后，映场随下个版本同步 `spec/cheer/`。
- **艺人专属 MIX**（`mix/artists/`）：授权按 §1（自己创作、开放许可或原作者同意），内容按 §2–§3（不是唱词，不含不当内容）；艺人名写法与这位艺人的应援文件一致，指定歌曲的歌名与录音一致。
