# 审核标准

维护者合并投稿前按以下顺序检查。自动检查（“检查”工作流）通过是前提；它管格式、文件位置、授权状态、许可与重复，下面几条需要人工判断。

## 0. 先看改了什么

- 投稿 Pull Request 只能改 `cheers/` 与 `mix/` 下的投稿文件（`mix/proposals/`、`mix/artists/`）；自动检查会拒绝把投稿和其他修改混在一起的 Pull Request。修改 `contributors.json` 的 Pull Request 等于改动“谁能自动合并”，须逐项核对。
- 自动检查用的是**基准分支**的检查代码，Pull Request 自带的 `lib/`、`tools/` 修改不会影响它的结果。反过来，修改 `lib/`、`tools/`、`tests/`、`spec/`、`.github/` 或 `package.json` 的 Pull Request，检查通过不代表修改正确，须逐行审查；工作流文件的修改尤其要看权限与触发条件。
- 本仓库设置为第一次投稿者的工作流须经维护者批准：在 Pull Request 页面先看一眼改动，再点 **Approve and run**。

## 1. 授权是否可信

- `original`：文件应是投稿者自己听写打轴的。看说明是否具体（例如怎样听写、参考了哪一场演出的录音）；如果与某份公开的 call 表或某个视频的时间轴几乎一样，请投稿者说明，必要时不收。
- `open-license`：打开来源链接，确认许可确实是 `license` 写的那一种，且允许修改与再分享；相同方式共享（SA）的来源只能以 `CC-BY-SA-4.0` 发布。
- `consented`：Pull Request 中须有原作者同意的链接或可核对的说明（例如原作者在公开页面上的回复）。只有截图、无法核对时，请投稿者补充。

## 2. 没有歌词原文

- 通读每条口号、call 与提示：应当是 MIX、成员名、短的喊声或动作提示，不是唱词。
- 跟唱的那一句应当用 `echo`，不写文字。
- 有疑问时，在映场中导入该文件并播放这首歌，再点“分享…”：映场会把文字与歌词逐行比对（`lyricOverlap`）。

## 3. 内容适当

- 不收侮辱、骚扰、歧视或涉及私人信息的内容；作者署名与链接只能是投稿者本人的。
- 不收与应援无关的文件。
- 某个组合专属的口号可以出现在那首歌的文件里，也可以作为艺人专属 MIX 投稿；内置 MIX 库（`spec/mix-library.json`）只收通用 MIX，见 §7。

## 4. 重复与更新

- 内容完全相同的文件，自动检查会拒绝。
- 检查提示“同一作者已有这首歌的版本”时，问投稿者是否要替换旧文件。
- 不同作者为同一首歌做的版本可以并存。

## 5. 合并

- 用 “Squash and merge” 合并，保留投稿者为作者。
- 合并后“更新索引”工作流会自动提交新的 `index.json`。如果它失败（例如推送时 `main` 已有新提交），在 Actions 页面选“更新索引”，点 **Run workflow** 从最新的 `main` 重新运行；不要用“重新运行”旧的那一次，它会取出旧提交。

## 6. 作者修改自己的文件（自动合并）

- 新投稿合并后，“更新索引”把那个 Pull Request 的作者（发起它的 GitHub 账号）记为文件的投稿者，写进 `contributors.json`。只有照 §5 用 Squash 合并、且 Pull Request 来自作者自己的仓库（fork）时才能这样对应；直接推送到 `main` 的文件记为推送者；用 “Create a merge commit” 合并时，新文件没有记录，运行日志会提示；用 Rebase 合并时，除最后一个提交外的新文件会记为点合并的维护者。所以投稿请一律用 Squash。删除文件时记录随之删除；只改名、内容不变时记录跟着文件走，改名的同时改了内容则算删除旧文件、新增新文件，记为这次提交的投稿者。
- 之后同一个账号发起的 Pull Request，只修改或删除它投稿的文件（`cheers/` 或 `mix/artists/` 下）、不是草稿、且“检查”在最新提交上通过时，“自动合并”工作流会把它 Squash 合并，再启动“更新索引”。比对的是账号的数字编号，不看用户名，也不看文件里的作者署名。
- 新增文件、改名、改动别人的文件或其他文件，都不会自动合并，照常按本标准审核。在 `main` 上新增或删除过、而记录还没更新的文件也不会自动合并。维护者随时可以手动合并，也可以修改 `contributors.json`（例如把记录改到作者的新账号）。
- 自动合并不经人工审核：作者事后改动的授权状态、许可、来源、署名，以及改进去的歌词原文或不当内容，都没有经过 §1–§3 的检查。发现或收到报告时，按本标准与下架规则处理。
- `contributors.json` 中的 `recordedThrough` 是记录已经处理到的 `main` 提交，下一次“更新索引”从它接着处理，所以某次运行失败或被取消，下一次运行（包括手动运行）会补上。补不上的只有那期间直接推送的新文件（已无法确认是谁推送的），运行日志会列出它们。不要手动修改 `recordedThrough`；遇到冲突时保留 `main` 上的值。
- 手动补记：等列出这个文件的那次运行的提交已经推送到 `main`（`recordedThrough` 已在新增这个文件的提交之后）再改 `contributors.json`，否则下一次运行会把记录当作过时的删掉。
- 重写 `main` 的历史（例如为下架清除历史）之后，`recordedThrough` 不在历史中了，工具会改从这次推送开始；如果那期间有新增文件，请手动补记。

## 7. MIX 投稿

先确认“检查”通过（格式、读音个数、编号与路径、来源链接、与内置库不重复都由它检查），再看：

- **通用 MIX 提议**（`mix/proposals/`）：
  - 是否通用：名称在应援圈公认，形式在各来源中基本一致；不含特定成员、组合、公演名或专属梗（成员名字只能是 `{name}` 空位）。属于某个组合的，请投稿者改投艺人专属 MIX。
  - 打开每个来源链接，确认能看到这条口号，且来源之间相互独立（不是互相转载）；只在单一来源出现、或来源之间差异大的不收。
  - 核对平假名与罗马音（逐词与整句），特殊读法要有 `readingNote`；`note` 是投稿者自己的话，不是照搬来源的说明。
  - 合并后“更新索引”会运行 `tools/accept-mix-proposals.js`，把它追加到内置库末尾（沿用已有来源代码或分配新代码）并删除提议文件；它失败时整次运行失败、不会只并入一半，修正后在 Actions 里手动运行“更新索引”。内置库变了之后，映场随下个版本同步 `spec/cheer/`。
- **艺人专属 MIX**（`mix/artists/`）：授权按 §1（自己创作、开放许可或原作者同意），内容按 §2–§3（不是唱词，不含不当内容）；艺人名写法与这位艺人的应援文件一致，指定歌曲的歌名与录音一致。

## 下架

收到下架请求时按[下架规则](./takedown.md)处理，不在这里等待审核流程。
