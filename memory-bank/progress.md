第二期按维护者授权推送（`main` `e896df9..3d037d1`），网站生效后核对：`/privacy/` 与 `/editor/youtube.js` 可访问；各页面实际返回的内容安全策略与预期一致（只有 `/editor/` 放行 YouTube 与 Bilibili，首页与 `/editor/mix/` 没有）。**线上实测**（内置浏览器，先强制取回最新文件）：打开制作页与输入链接都没有第三方请求；YouTube 官方示例视频加载（播放器 400×225）、播放、标记起点；外部播放的手动对时；控制台无报错。

**发现的问题**：站点的脚本与样式带着 `Cache-Control: max-age=14400`（4 小时，自定义域名上由托管方加的；页面本身是 `max-age=0`）。所以每次更新后的 4 小时内，最近来过的访客会拿到新页面配旧脚本——这次的表现是“贴视频链接…”等新按钮点了没反应，强制刷新后正常。这个问题以前每次更新都存在，只是这次新按钮多才显出来。

**修复（本地提交，未推送）**：`tools/build-site.js` 给页面和脚本里出现的每个本站脚本、样式地址带上本次构建的版本号（全部源文件内容的哈希前 10 位），脚本之间的 `import` 与节拍分析线程的地址也一样。新页面只会请求新文件，同一次构建的文件只会一起使用。新增一项测试（全站只出现一个版本号、每个地址都带、源文件一变版本就变），原有三处钉住地址的断言随之更新。已验证：382 项测试通过；本机按站点响应头打开制作页，8 个脚本与样式都带版本号加载，无报错。未验证：线上效果（推送后才能看）。在推送之前，线上仍有这个问题：功能不响应时强制刷新（⌘⇧R）即可。

## 2026-11-26 贴视频链接：第二期（已于同日上线，见上一条）

决定见 C-016 ④。分支 `claude/play-without-audio`，在第一期之上。

- 时间来源多了“视频”一类（`site/editor/timesource.js` 的 `useVideo`）：播放器报告自己的位置，编辑器的时间是“视频时间 − 歌曲起点”。
- YouTube（`site/editor/youtube.js`）：只用官方 IFrame Player API。位置每 250 毫秒读一次，之间按页面时钟推进；用户拖 YouTube 自己的进度条也能跟上。可以标记“歌从这里开始”、按 0.1 秒微调、标记“歌到这里结束”定时长。上传者禁止嵌入、视频不存在、连不上，各有提示与出路。
- Bilibili：官方外链播放器放进页面（沙盒框架：能播放、能在新标签打开 B 站，但不能把本页带走），应援走无声计时，手动对时。外部播放（视频或歌在别处放）同样手动对时：开始、暂停 / 继续、提前 / 推后 0.1 秒、从头对齐，累计微调常显。
- 链接只经 `lib/video.js` 解析（白名单平台与编号格式），页面从不把用户输入拼进地址；不支持短链。链接、起点、微调只存在浏览器本地（按应援记住最近 20 个），再次打开时只提示、不自动加载。
- 内容安全策略只在制作页放开：脚本多一个 `https://www.youtube.com`，框架多 `https://www.youtube.com`、`https://player.bilibili.com`、`https://www.bilibili.com`。其他页面不变。
- 新增隐私说明页 `/privacy/`（页脚有链接），加载 YouTube 视频前的说明里带 YouTube 服务条款与 Google 隐私权政策的链接——这是 YouTube API 服务对使用方的要求。
- 链接解析由 Codex 按定好的接口实现；其余由 Claude 写。

**与设计不同的两处**：①原想把 YouTube 的脚本关进沙盒小页面，实测不行（沙盒页面没有来源地址，播放器无法与它通信），所以脚本直接加载在制作页，仍是用户点“加载视频”之后才加载。②YouTube 的条款要求播放动作“清楚地标明是 YouTube 的动作”，所以用 YouTube 视频时播放按钮写作“播放 YouTube / 暂停 YouTube”；条款还要求播放器不被遮挡，所以视频面板固定在页面上方，矮屏幕上底部播放条不再悬浮。

**已验证（本地）**：测试通过（数目见提交说明）；按站点自己的响应头在本机走查：不贴链接、恢复带视频的草稿时都没有任何第三方请求；贴链接对话框对短链、不支持的网站、Bilibili、YouTube 各给出正确提示；YouTube 用官方文档的示例视频实际加载、播放、从页面跳转、标记起点并微调、暂停，页面时间跟随；Bilibili 与外部播放的手动对时全流程。Bilibili 播放器用无界面 Chrome 截图确认在沙盒框架里能显示出封面与播放按钮，且没有自动播放。

**合入前独立审查**（Codex 只读，第一轮）：4 项阻止合入、7 项建议，逐条核实后全部修复——①“歌到这里结束”（以及第一期已上线的手填时长）可以把时长改到已有应援之前，得到一份本页自己都拒绝打开的文件：现在会说明有几条应援在后面并拒绝改动；②恢复视频后第一次加载失败、点“重试”成功，会把作者标好的歌曲起点写成 0：失败状态现在带着起点；③还在加载的 YouTube 请求晚到时，会把刚换上的 Bilibili 播放器从页面上清掉：加载前先确认自己仍被需要，销毁时只移走自己的节点；④YouTube 的接口脚本到了、播放器却一直不应答时，页面永远停在“正在连接”：给播放器就绪单独设了超时。建议里的：视频时长晚到时控件不启用；采样与状态事件抢先导致漏报“开始播放”（改为只在一处读状态、每个变化只通知一次）；在播放器自己的菜单里改倍速页面不知道；本地草稿改了时长就找不到上次的视频；一条损坏的历史记录拖垮其他视频的加载；Bilibili 起点不能填 0:00 或超过两小时；本站对话框会盖住正在播放的 YouTube 播放器（现在对话框打开时视频暂停、播放器暂时让开），从“上次的视频”直接加载时没有条款链接；手动对时播完后“继续”会带着上一轮的微调从头再来。取舍：对着 Bilibili 或外部播放手动对时也算“对着视频制作”。新增 `tests/youtube.test.js`（5 项）覆盖其中 ②以外的几条；② 在界面逻辑里，没有单元测试，靠走查。

**第二轮复审**（同一 Codex 会话，按规则这是最后一轮）：上轮四项里三项确认修好；仍有两项阻止合入，另有四条上线前应知道的风险。阻止合入的两项已在复审之后修复，**没有再送审**（审查以两轮为限，是否上线交维护者定）：①重试用的是加载时的起点，作者之后重新标记再遇到播放器出错，重试会把起点写回旧值——现在取出错那一刻的起点；②上一轮把“记住视频”放进了草稿保存，一条时间戳损坏的历史记录会让排序抛错、草稿存不上——现在记住视频出什么错都不影响草稿，历史记录读出时把时间戳归一。风险里修了三条：视频时长晚到时自动补时长不再记为“对着视频制作”；时长晚到时也核对记住的起点是否超出视频；缓冲中打开对话框、随后才开始播放的视频会被再次暂停。留下一条已知限制：同艺人、同歌名的两个本地版本（如录音室版与现场版）共用一条视频记忆，后存的会替换先存的（加载仍要用户点击；社区文件按路径区分，不受影响）。复审后的修复在浏览器里验证了“损坏的历史记录不影响草稿保存”，重试那条只读了代码。

## 手动填写 BPM 与起拍偏移（2026-10-29，已上线）

试用者反馈：音频的第一拍不在 0:00 时，需要能填 offset（参照其他打谱工具的“BPM + Offset”）。此前网页编辑器的节拍网格只能自动分析或跟拍 8 下得到，修正只有 ×2、÷2、移一拍，没有地方直接填速度和起拍位置；“更多”里的“整体偏移”移动的是整份应援，不是拍子线。维护者决定先加手动 BPM 与起拍偏移，多段变速与变拍号先不做（2026-10-29 对话：“加 BPM 与偏移”）。

- 底栏节拍按钮组与“更多”各加入口“BPM 与起拍偏移…”，打开对话框：节拍速度（40–320 BPM，可带小数）、起拍偏移（秒，按音频时间，0 到歌曲长度）、“设为当前播放位置”（播放中点击时减去反应补偿，与跟拍一致）、有自动分析结果时“恢复自动分析的结果”。网格仍是单一速度、4/4 拍，只用于对齐 MIX、逐词对齐与推荐，**不写进应援文件，格式不变**。“整体偏移”下加一句说明两者区别。
- `lib/suggest.js` 新增 `GRID_BPM` 与 `gridFromBPM`（来源记为 `manual`，推荐把握与跟拍相同，为“中”）；×2 / ÷2 的范围改读 `GRID_BPM`（数值不变）。只在网页端，映场编辑器没有手动网格。
